# ZhangData 项目知识库稳定背景 v5.1

生成日期：2026-04-30
适用范围：NotebookLM 长期知识库稳定包。除非项目架构、核心模块边界或主版本发生明显变化，否则不需要频繁替换。

## 1. 项目一句话定义

ZhangData 是一个面向 A 股中期波段研究的本地金融研究工作台。它不是券商交易终端，也不是自动交易系统，而是把实时盯盘、盘后复盘、L2 资金结构、策略研究、题材热度和人工判断放在同一套工作流里，帮助用户判断“哪些票值得继续研究、为什么值得研究、风险在哪里”。

项目的核心目标不是预测每一只股票明天涨跌，而是建立一套可复盘、可解释、可迭代的研究系统：

- 盘中知道重点股票发生了什么；
- 盘后能用统一图表复盘价格、成交、资金和事件；
- 选股模块能给出候选、理由和风险，而不是只给黑盒分数；
- 热点板块研究能解释市场主线和拥挤度，但不会被直接误用成买入信号；
- 所有结论都要能回到数据和历史样本验证，不靠感觉扩写。

## 2. 用户交易目标与研究偏好

用户关注的是 A 股中期波段，不是高频，不是纯打板，也不是长线基本面选股。典型持仓周期大约是一周到一两个月。主要目标是抓中小票趋势行情，尤其是资金提前介入、启动后有承接、后续仍有扩散空间的机会。

用户不希望系统变成：

- 只追当天暴涨或短线连板；
- 只因为题材热就推荐买入；
- 只输出一堆不可解释的指标编号；
- 用极细阈值过拟合历史；
- 把少量回测样本包装成稳定策略；
- 把研究候选误称为交易指令。

用户更需要系统回答：

- 这只票是否有真实资金介入，而不是单纯价格异动；
- 当前是启动、洗盘承接、趋势中继、补涨扩散，还是高潮接盘；
- 候选票属于什么题材，题材是新启动、持续发酵，还是已经拥挤；
- 如果买点成立，主要风险是什么；
- 如果买点失败，历史上类似失败样本有什么共性。

## 3. 核心数据观：L1、L2 与原子事实层

ZhangData 的研究优势来自本地沉淀的盘后 L2 成交与挂单数据。这里的 L2 不是神奇预测器，而是比普通行情更细的市场行为记录。

### L1 数据

L1 主要是普通行情层，包括价格、成交量、分时、K 线、涨跌幅、成交额等。L1 可以回答“价格发生了什么”，但很难回答“资金结构为什么这样变化”。

### L2 数据

L2 更接近盘口与成交细节，可用于观察：

- 主力净流入、超大单净流入、大单主动买卖；
- 买盘和卖盘挂单强弱；
- 撤买单、撤卖单、盘口支撑是否真实；
- OIB、CVD 这类主动成交方向指标；
- 成交和挂单之间是否背离。

项目里对 L2 的使用原则很保守：L2 能提高解释力，但不能单独替代策略闭环。比如“超大单净流入”不等于一定上涨，“L2 龙头过滤”能提高未来强股命中率，但不一定改善收益。系统会把 L2 当成验证资金行为的证据，而不是万能买点。

### 原子事实层

原子事实层是把分散的原始数据处理成可复用的日级事实。例如某只股票某天的主力资金、超大单、价格位置、涨停状态、量能、盘口特征、事件标签等。它的价值是让复盘、选股、热点研究用同一套事实语言，不再每个模块各算各的。

判断项目结论时，要注意数据覆盖范围。某些策略依赖完整 L2 挂单数据，如果历史早期没有挂单字段，不能把那段历史的失真结果当成策略真实性能。

## 4. 三端架构：为什么分成 Windows、Mac、Cloud

ZhangData 不是单机网页项目，而是三端协同系统。这个架构来自实际约束：A 股数据外采容易受 IP、速度、稳定性和数据体积限制；L2 原始包很大；云服务器只适合轻量服务；Mac 是用户日常开发和研究环境。

### Windows 数据主站

Windows 是唯一正式外采节点和正式跑数工厂。它负责盘中实时 crawler、盘后 L2 和原子事实层处理、正式研究库产出、向云端喂轻量盯盘数据、向 Mac 同步处理后的研究数据。

Windows 的角色不是写文档或日常开发，而是数据真相源。所有重数据、原始包、大规模处理优先在 Windows 完成。

### Mac 本地研究站

Mac 是用户的主工作台，负责代码修改、文档治理、本地前后端运行、复盘、选股、策略研究和 Codex 协作。Mac 默认消费 Windows 同步过来的正式库，不应该长期直接跑生产级外采 crawler，也不应该跨网络直接读 Windows SQLite 主库。

Mac 上的本地服务是研究站，不是云端生产替身。它的意义是让用户在本地快速分析、复盘、改代码、验证策略。

### Cloud 轻量盯盘

Cloud 负责线上轻量盯盘和手机应急查看。它接收 Windows 的 ingest，提供轻量 API 和前端访问，但默认不主动外采，不承载 full atomic 或 selection 研究主查询。

Cloud 的原则是轻、稳、被动。它不是研究主库，也不是数据工厂。

## 5. 当前已落地的三大核心模块

当前项目真正落地的主模块是三条：盯盘、正式复盘、选股研究工作台。

### 5.1 盯盘模块

盯盘模块解决盘中“重点股票正在发生什么”的问题。它不是全市场雷达，而是精细化 watchlist。用户关注几十只核心股票，系统追踪这些股票的价格、成交、资金、分时与盘口变化。

典型链路是：前端页面声明当前活跃股票，Windows crawler 读取活跃股票和自选池后外采行情，再把快照和逐笔数据写入云端轻量库。线上页面读取云端接口，Mac 本地页面默认读取本地同步库。

盯盘模块关注的不是“所有股票都扫一遍”，而是对已有关注池进行高频观察。它可以帮助用户发现：

- 某只票突然放量或资金异常；
- 盘口是否有真实承接；
- 分时上冲是否伴随主动买入；
- 当日表现是否与历史复盘逻辑一致；
- 盘中是否需要标记为后续复盘对象。

盯盘的主要风险是数据源和进程稳定性。系统需要保证 crawler 不重复启动、不读错库、不把云端当外采源、不让单一行情源失效导致无感知假空。

### 5.2 正式复盘模块

正式复盘模块解决“盘后如何统一看历史多周期图和资金结构”的问题。它是用户每天研究股票时的核心页面之一。

复盘页面的重点不是展示漂亮 K 线，而是把多个粒度的信息放到同一张研究图里：

- 5 分钟、15 分钟、30 分钟、60 分钟、日线等多周期；
- 价格走势与成交量；
- L1 / L2 资金流；
- 主力、超大单、主动买卖；
- 策略节点和事件锚点；
- 过去关键日与当前信号之间的关系。

正式复盘和沙盒复盘是隔离的。沙盒页面可以保留用于历史验证或兼容跳转，但当前正式主路径是正式复盘页面。正式复盘不能依赖临时实验口径，也不能让旧兼容链路污染正式判断。

复盘模块的核心价值是把“为什么这只票当时应该看出来”变成可回看的证据链。它服务于策略迭代，也服务于人工盘后判断。

### 5.3 选股研究工作台

选股模块当前定位是研究与观察工作台，不是稳定自动买入系统。它已经从早期单策略候选页推进到每日复盘决策入口。

当前选股工作台做的事情包括：

- 按日期汇总多个策略结果；
- 给出明日可操作、观察中、风险拦截等候选分组；
- 对每只候选显示策略理由、资金结构、风险信号；
- 右侧提供波段复盘图，让用户判断策略节点是否可信；
- 把候选与历史走势、L2 资金、事件解释联系起来。

选股模块的正确使用方式是“候选生成 + 人工复核 + 滚动验证”。它不能被理解为自动下单系统。尤其是策略样本少、覆盖面窄、数据不完整或热点逻辑未验证时，必须保持保守口径。

## 6. 当前主要策略知识

### 6.1 资金流回调稳健策略

这是当前质量较高的主策略。它不是追当天暴涨，而是寻找资金先出现异动、价格确认启动、启动后第一次回调被资金承接的机会。

业务逻辑可以理解为：

1. 先发现资金和价格结构异常；
2. 等启动确认；
3. 启动后不立刻追，而是等待第一次回调；
4. 如果回调时资金仍有承接，确认日收盘识别；
5. 次日开盘作为观察买点；
6. 买入后重点看累计超大单是否从峰值真实撤退；
7. 买入前用组合风险过滤明显危险票。

这条策略的关键不是单日资金净流入，而是“启动后回调时是否有人接”。它试图避免追高，抓的是资金已经介入但尚未完全走完的波段。

历史成熟口径显示，组合风险过滤后样本少但质量较高。当前应把它作为观察盘和模拟盘优先策略，而不是直接实盘自动买入。

### 6.2 组合风险过滤

组合风险过滤的理念是：单个风险信号可能误杀，但多个风险同时出现时，危险性明显增加。

典型风险包括：

- 启动期撤买单异常，说明看似强的买盘可能在撤梯子；
- 盘口买盘强但主动成交弱，说明挂单不一定转化为真实买入；
- 确认日出货分偏高；
- 确认日超大单和主力资金同时为负；
- 弱启动且回调承接差。

NotebookLM 在解释策略时应强调“组合风险”而不是把任一单因子说成绝对风险。

### 6.3 趋势中继高质量回踩策略

趋势中继策略的目标是补足资金流回调稳健策略覆盖面窄的问题。很多强势股不是低位启动后标准回调，而是在趋势已经形成后继续主升。直接追趋势中继历史表现很差，因为会混入大量假中继和冲高回落票。

因此当前版本只保留“高质量回踩中继”方向：

- 先识别强趋势观察池；
- 不在入池当天直接买；
- 等二次买点，例如回踩均线承接、缩量震荡后放量阳线、强分歧后修复、前高附近震荡但不出货；
- 再用 L2 和价格结构确认。

当前严格高质量回踩样本表现很好，但样本数量仍少。正确口径是“方向值得前向观察”，不能说已经充分稳定。

## 7. 热点板块研究的稳定定位

热点板块研究当前属于探索能力，但它对项目很重要，因为用户不能在不知道市场主线的情况下研究股票。

这里的关键原则是：热点不是买点，而是上下文。热点可以帮助回答：

- 这只票为什么被市场关注；
- 它属于哪个细分主题；
- 这个主题处于新启动、持续发酵还是高潮拥挤；
- 候选票是板块核心、容量票、补涨票，还是孤立异动；
- 对 breakout 类策略，它是否已经太拥挤；
- 对低位潜伏类机会，它是否处于热点扩散早中期。

项目已经明确避免把“题材热”直接当作加分项。因为历史验证说明，热点能解释未来强股更容易从哪里来，但热点池内部后排票太多，直接买并不能稳定赚钱。对已经 breakout 的票，热点共振甚至可能代表追高和高潮风险。

因此 NotebookLM 回答热点相关问题时，要区分：

- 解释力：热点能解释强股来源；
- 交易力：热点本身不能直接产生买点；
- 风险力：某些热点阶段会提示拥挤和接盘风险；
- 研究力：热点低位 L2 补涨是可继续观察的策略雏形。

## 8. 项目管理与文档治理原则

项目内部文档分为长期事实、契约、运维、变更过程和归档。NotebookLM 不需要背文件路径，但需要理解治理原则：

- 长期事实要和当前系统真实状态一致；
- 新能力不能只改代码，必须有变更卡和验收记录；
- 接口、数据结构、业务规则、运维步骤不能互相覆盖；
- 已验证结论、探索中假设、失败实验要区分记录；
- 旧链路可以兼容保留，但不能被说成当前正式主路径；
- 任何策略结论都要标注适用数据周期、样本规模和限制。

对 NotebookLM 来说，最重要的是不要把文档中的“当前探索”“下一步计划”误读成“已经上线稳定能力”。

## 9. NotebookLM 回答本项目问题时的规则

当用户询问 ZhangData 时，NotebookLM 应按以下方式回答：

1. 先判断问题属于盯盘、复盘、选股、热点、数据链路、运维还是文档治理。
2. 明确当前状态：已落地、部分落地、探索中、已否决、待验证。
3. 对策略问题，必须说明这是研究候选、观察盘还是可前向验证方向，不应直接给实盘买卖建议。
4. 对热点问题，必须区分“解释强股来源”和“能不能直接买”。
5. 对历史结果，必须同时提到样本周期、样本量、胜率、Alpha 或覆盖面限制。
6. 如果用户问“今天/最近”，必须优先查看最新日期更新包，而不是只看稳定背景包。
7. 如果稳定背景包和日期更新包冲突，以日期更新包中明确标注的最新研究状态为准；但长期架构边界仍以稳定背景包为准。
8. 不要把本地文件结构当成答案重点。文件名只有在用户明确问“在哪里改/在哪里查”时才有意义。
