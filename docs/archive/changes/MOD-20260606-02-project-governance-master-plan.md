## 2. 背景与目标

当前仓库已经连续开发数月，且长期由 AI 并行推进。现在的问题不再只是“有没有脏文件”，而是三类问题混在一起：

1. 已经做完的业务线还留在本地未提交，导致“当前真相”和“待治理项”混淆。
2. 仓库内存在冗余脚本、历史数据库、阶段性资料和高曝光入口文档漂移。
3. 运行架构已经从旧云端中心口径，演进到 `Mac + Windows + NAS` 协作，但文档、脚本、配置、发布链未完全统一。

这次治理的最终目标不是“简单删文件”，而是把项目收口到可持续维护状态：

1. 文件、文件夹、数据产物边界清晰。
2. 核心文档与当前系统真相对齐。
3. `Mac / Windows / NAS` 三端职责、路径、发布方式和协作规则固定下来。

## 3. 这次治理的总原则

### 3.1 先收真相，再做清理

先把“已经完成但还没收口”的业务线提交或正式归档，再做全仓盘点。否则盘点结果会一直混入“未提交功能”和“真实垃圾”。

### 3.2 先按业务目标判断，不按文件名判断

每条线先回答两个问题：

1. 它原本想解决什么业务问题？
2. 这个业务目标现在是否已经达成？

只有在业务目标明确后，才决定：

- 收口提交
- 回写文档
- 下沉归档
- 标记待清理
- 彻底删除

### 3.3 禁止一锅端

本轮治理必须按主题分批推进，不能把下列内容混成一笔：

1. `星火双轨 / 试盘 / model-research`
2. `NAS / research-current`
3. 三端真相文档
4. 全仓大文件与冗余脚本治理

### 3.4 删除前先证明“无引用”

任何数据库、脚本、目录、文档，在进入删除动作前，必须先完成：

1. 当前真实用途判定
2. 代码 / 文档 / 脚本引用搜索
3. 替代入口确认
4. 回退方案确认

### 3.5 明确本轮不做什么

本轮治理默认不处理：

1. `docs/portfolio-ops/*`
2. 外部 `market-data` 主数据目录的物理迁移
3. 与当前治理主题无关的 UI 重构
4. 未经验证的大规模历史文档重写

## 5. 总体执行顺序

### Phase 0. 真相基线固定

目标：确定“从哪一个提交点开始做治理”。

动作：

1. 以 `main` 当前最新提交为基线。
2. 记录当前未提交改动清单。
3. 把已完成业务线与未完成治理线分开。
4. 固定“本轮不纳入”的主题。

产物：

1. 本卡
2. 当前工作区脏改清单
3. 主题边界说明

通过标准：

- 能明确说出“哪些是已完成未提交、哪些是真待治理、哪些不纳入本轮”。

### Phase 1. 收掉剩余两条本地真相线

#### 1A. 收 `NAS / research-current`

目标：判断这条线是不是已经达到业务目标，并把真正需要保留的实现与文档收掉。

业务目标定义：

1. 运行时数据口径已从单一目录拆为 `LIVE_DATA_ROOT` 与 `RESEARCH_CURRENT_ROOT`
2. 本地正式研究库可以发布到 NAS `research/current`
3. NAS 侧前后端可以按新口径启动与读取
4. 发布、回滚、检查、冒烟具备最小闭环

执行动作：

1. 核对配置、脚本、compose、ops、测试是否围绕上述 4 个目标闭环。
2. 区分“正式保留对象”和“过程性临时脚本”。
3. 回写入口文档，清除仍写成旧云端 / 旧 flat 目录的高曝光表述。
4. 单独提交，不和别的线混提。

通过标准：

- 能独立提交一笔 `NAS / research-current` 收口改动。

#### 1B. 收三端真相文档

目标：把高曝光入口统一成当前三端口径。

最低收口对象：

1. `README.md`
2. `docs/AI_QUICK_START.md`
3. `docs/04_OPS_AND_DEV.md`
4. `docs/07_PENDING_TODO.md`
5. `docs/AI_HANDOFF_LOG.md`

业务要求：

1. `Mac` 是开发与本地研究控制台
2. `Windows` 是数据主站 / 跑数节点
3. `NAS` 是在线运行节点 / 发布节点
4. 发布默认路径、Git 入口、远程管理方式写清
5. 已完成事项不再继续挂在 `07_PENDING_TODO`

通过标准：

- 高曝光入口不再互相打架。

### Phase 2. 全仓真相冻结与资产盘点

目标：在“剩余真相线收口后”，对整个仓库形成可信 inventory。

动作：

1. 盘点 Git 受控文件、未跟踪文件、超大文件。
2. 盘点仓库内所有数据库、CSV/JSON 研究产物、脚本族、缓存、部署文件。
3. 按用途分类：
   - 正式运行资产
   - 正式研究资产
   - 文档/资料资产
   - 历史兼容资产
   - 候选归档资产
   - 候选删除资产
4. 对所有 `>100MB`、`>500MB`、`>1GB` 文件做单独表。

本阶段关键原则：

1. 不急着删。
2. 先形成清单，再决定动作。
3. 仓库内数据库与外部 `market-data` 主库必须分开看。

产物：

1. 文件资产盘点表
2. 大文件清单
3. 数据产物角色清单

通过标准：

- 能回答“这 8G 分别是什么、谁在用、哪些该保留、哪些只是历史残留”。

### Phase 3. 文件治理

目标：把仓库物理层收紧到长期可维护。

治理对象：

1. 历史脚本
2. 仓库内历史数据库 / shadow db / sample db
3. 重复导出物
4. 阶段性实验结果中不应长期顶层保留的内容
5. 不再是正式入口的部署或启动脚本

执行顺序：

1. 先归档，再删除。
2. 先下沉目录，再删顶层噪音。
3. 先修入口引用，再移动文件。

对每个候选对象，必须给出 4 选 1 结论：

1. 保留为正式对象
2. 下沉归档
3. 标记兼容对象
4. 删除

通过标准：

- 仓库根目录与高频目录不再堆满历史工具和歧义产物。

### Phase 4. 文档治理

目标：让“读文档的人”看到的就是当前系统真相。

执行动作：

1. 对照当前代码和脚本，核查核心文档是否失真。
2. 对高曝光入口做统一：
   - 项目真相
   - 数据根目录
   - 正式脚本入口
   - 发布路径
   - 候选源与研究页入口
3. 将大量过程材料继续压缩为：
   - mother card
   - short log
   - archive summary

重点检查：

1. 文档写成“未完成”，但代码已完成
2. 文档写成“当前入口”，但实际上只是兼容路径
3. 文档仍引用旧环境、旧服务、旧目录

通过标准：

- 核心文档与系统行为不再互相矛盾。

### Phase 5. 三端协作对齐

目标：把 `Mac / Windows / NAS` 的职责、数据路径、同步和发布规则固化。

必须固定的真相：

1. 哪一端负责开发
2. 哪一端负责正式跑数
3. 哪一端负责在线服务
4. 正式数据根目录分别在哪里
5. 每日跑数链、发布链、回滚链怎么走
6. 哪些方式是正式路径，哪些只是 fallback

执行动作：

1. 统一环境变量与路径口径。
2. 统一 runbook。
3. 补齐最小 smoke checklist。
4. 把“可验证但未固化”的口径收成正式规则。

通过标准：

- 新 AI 或新维护者能按文档独立完成一次日跑、发布、检查和回滚。

### Phase 6. 验证与删改闭环

目标：确保治理不是“看起来整洁”，而是真可运行。

最小验证集：

1. 相关 pytest
2. 关键脚本 dry-run / help / path check
3. 本地前后端启动验证
4. NAS 发布链最小冒烟
5. 文档入口抽检
6. 大文件与删除对象复核

通过标准：

- 每一项删除、归档、改入口，都有对应验证证据。

### Phase 7. 最终收口

目标：把这轮治理压成长期可继承状态。

动作：

1. 更新 `AI_HANDOFF_LOG`
2. 清理 `07_PENDING_TODO` 已完成项
3. 如有需要，把阶段性治理卡归档
4. 给出最终遗留问题与下一轮边界

通过标准：

- 后续再开新会话时，不会重新把已完成事项当成当前问题。

## 6. Goal 模式执行规则

如果后续进入目标模式，执行必须按以下规则：

1. 严格按 `Phase 1 -> Phase 7` 顺序推进，不允许跳过 `Phase 1` 直接做全仓清理。
2. 每个 phase 结束后，先更新状态，再进入下一个 phase。
3. 一次只推进一个主主题；若并行，只允许让子代理做不重叠的子问题。
4. 删除动作必须在“已形成盘点清单”之后执行。
5. 任何业务目标不清楚的主题，先回到“目标确认”，不脑补。

## 7. Agent 架构建议

总控 Agent 负责：

1. 维护阶段顺序
2. 裁剪提交边界
3. 决定是否删除 / 归档
4. 回写核心文档

可并行的子 Agent 分工：

1. `runtime-closure`：核配置、脚本、测试、compose、部署链
2. `docs-truth`：核高曝光文档与代码真相是否一致
3. `inventory-audit`：核大文件、数据库、脚本族、目录角色
4. `cleanup-verifier`：核候选删除对象是否仍被引用

要求：

1. 子 Agent 只能做边界清晰、写集不重叠的任务。
2. 真正的删除、归档、提交边界判断由总控 Agent 最终拍板。

## 8. 验收标准（Given / When / Then）

- Given 仓库当前仍存在 `NAS / research-current` 与三端真相文档未收口、全仓 8G 未盘点、入口文档存在漂移。
- When 按本卡从 `Phase 1` 顺序执行到 `Phase 7`，并完成每阶段验证。
- Then 应达到以下结果：
  1. 已完成业务线全部正式收口；
  2. `NAS / research-current` 与三端协作口径固定；
  3. 仓库文件资产有清单、有角色、有删改依据；
  4. 核心文档与系统当前行为一致；
  5. `Mac / Windows / NAS` 协作可按文档重复执行；
  6. 后续维护者不会再把历史残留误认成当前主线。

## 9. 风险与回滚

主要风险：

1. 把“未提交功能”误判为“应删除垃圾”
2. 把 NAS 迁移过程产物和正式发布链混在一起提交
3. 在未形成 inventory 前先删大文件
4. 只改文档，不改真实入口

回滚原则：

1. 每条主题线单独提交
2. 删除前先移动 / 归档
3. 高风险目录治理优先使用独立提交回退
