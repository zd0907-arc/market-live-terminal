## 2. 背景与目标
- 当前项目已经形成多个正式页面、研究页面、专题页面、策略研究目录、过程卡、实验脚本和运行产物。
- 代码层已经有一部分共享组件和共享页面壳，但页面、研究专题、过程文档、历史脚本仍然并行堆积。
- 当前最现实的问题不是“马上重构代码”，而是：
  1. 先把系统现在到底有哪些模块、页面、能力盘清楚；
  2. 先把明显过时、错误、会误导实现过程的过程材料降噪或清走；
  3. 再决定后续哪些代码/文档/脚本需要进一步收口。
- 用户当前最优先目标已经明确：**先清一波过程材料堆积，优先降低过时信息对后续开发的干扰。**

## 3. 本轮结论摘要

### 3.1 当前系统产品面
当前系统已经形成三层结构：

1. **主链产品层**
   - `盯盘首页` `/`
   - `正式复盘页` `/review`
   - `选股研究工作台` `/selection-research`

2. **研究主线层**
   - `市场热点` `/market-heat`

3. **实验 / 专题层**
   - `趋势研究` `/trend-research`
   - `模型训练` `/model-training`
   - `PPO 回测复盘` `/selection-ppo-report`、`/model-training/ppo-backtest`
   - `机会发现交易复盘` `/selection-opportunity-review`
   - `热点低位样本` `/market-heat/low-position-samples`

### 3.2 当前代码复用面
当前前端已经存在一条共享壳主线：
- `MarketTopHeader`
- `StockQuoteHeroCard`

- `HistoryMultiframeFusionView`

但同时仍有 4 类明显平行实现：

4. 首页和复盘页共享了一部分组件，但页面主体仍是两套大页面。

### 3.3 当前文档 / 脚本噪音面

- `README.md`
- `docs/00~08`

但高噪音区也很明确：

## 4. 当前治理判断

### 4.1 现在不应该先做什么
本轮不应该直接进入：
- 大范围前端重构；
- 首页/复盘/选股三大页面的合并改写；
- 大规模脚本删除；
- 一口气重写全部核心文档。

原因很直接：
- 当前最大风险不是代码暂时不好看，而是**错误文档和过时过程材料仍在持续误导后续实现**。
- 如果不先把“什么是当前真相、什么只是历史过程”分层清楚，后面无论删脚本还是改页面，都容易误删或误改。

### 4.2 现在最该先做什么
本轮的第一优先级应收敛为：
1. 先做**系统地图**；
2. 再做**过程材料降噪**；
3. 再做**历史材料归档与阶段汇总**；
4. 再做**重复实现/复用治理**；
5. 最后才进入**定向收口和清理执行**。

## 5. 执行规划（分阶段）

### Phase 1：系统地图冻结
目标：先把“当前系统是什么”固化成可读、可交接的总图。

要做什么：
1. 输出当前页面 / 模块清单；
2. 标记每个模块的定位：
   - 主链
   - 研究主线
   - 实验/专题
   - 兼容/维护态
3. 记录每个模块的核心功能；
4. 记录每个模块依赖的主要数据源和核心入口文档。

怎么做：
1. 以 `src/App.tsx` 为路由真相源；
2. 以 `docs/domain/*` 与 `docs/contracts/*` 为能力/契约真相源；
3. 只回填“现在真实存在的产品面”，不回填历史想法。

产出物：
1. 一份系统地图文档；
2. 一份页面/模块与数据源对照表。

验收标准：
- 用户能一眼看出系统当前到底包含哪些主页面、研究页、实验页；
- 后续 AI 不需要翻大量过程卡，也能知道当前产品面。

### Phase 2：过程材料降噪（第一优先级）
目标：优先处理会误导实现过程的过时材料，并先做“止血”。

当前执行进度（2026-05-19）：
1. `docs/changes` 第一批高风险现状型过程卡已补顶部提示；
2. `docs/strategy-rework/handoff-for-next-ai.md` 已降级为历史交接材料；
3. `docs/strategy-rework/README.md`、`docs/selection/selection_research_master.md`、`docs/04_OPS_AND_DEV.md` 已补“唯一先读入口”约束；
4. 下一步重点已转到 Phase 3，不再继续靠“只加提示”推进。

要做什么：
1. 盘点所有“当前仍会被 AI / 人误读为真相”的过程材料；
2. 按风险分层：
   - `P0`：内容已过时且现在会直接误导开发；
   - `P1`：内容已过时，但更多是噪音，不一定直接误导；
   - `P2`：历史研究资产，可保留，但不应作为默认入口；
3. 对 `P0` 材料做优先处理：
   - 从一级入口移除；
   - 明确标记“历史过程 / 先看新母卡”；
   - 必要时归档或迁移；
4. 对 `P1` 材料做第二轮降级；
5. 对 `P2` 材料只做目录分层和入口收口，不急着删。

怎么做：
1. 优先处理下列区域：
   - `docs/changes/`
   - `docs/strategy-rework/`
   - `docs/selection/`
   - `ops/` 中 atomic/backfill/bench 相关脚本说明
2. 先做“入口收口”和“标记降级”，不直接大删；
3. 删除动作必须建立在：
   - 当前无正式引用；
   - 当前无主链运行职责；
   - 已有更高层母卡承接真相。

产出物：
1. 一份过程材料分级清单；
2. 一份拟清理 / 拟归档 / 拟降级清单；
3. 一张专项清理执行卡。

验收标准：
- 默认阅读路径不再把过时卡和旧实验资料暴露成“当前真相”；
- 用户和 AI 进入仓库后，优先读到的是当前真相，而不是历史过程。

### Phase 3：历史材料归档与阶段汇总
目标：不只是“把旧文件留着加提示”，而是实际减少未来 AI 和人工反复读垃圾材料的成本。

要做什么：
1. 对已经确认属于历史过程的文档和材料，执行真实归档；
2. 对零散过程卡做主题级压缩，形成少数几份阶段汇总；
3. 让未来阅读者优先看到“阶段总结”，而不是几十张散落过程卡。

怎么做：
1. 先完成 Phase 2 的风险分级和入口降噪；
2. 再对 `P0/P1` 材料分三类处理：
   - `A. 保留原位，仅补提示`
   - `B. 迁移到 archive/ 或专题 archive 子目录`
   - `C. 有用信息吸收到阶段汇总后，从顶层入口层移走`
3. 归档时遵守：
   - `docs/archive/ARCHIVE_NAMING_STANDARD.md`
   - `docs/archive/ARCHIVE_CATALOG.md`
4. 对归档后的大主题，补一份“阶段汇总”文档，承接仍有长期价值的信息。

阶段汇总建议产出：
1. `v2.x -> v3.x` 早期能力与架构演进摘要
2. `v4.x` 数据链路、L2、ETL、架构收口阶段摘要
3. `v5.x` 本地研究站、复盘、选股、热点研究阶段摘要
4. 主题级摘要：
   - 选股策略研究阶段摘要
   - 市场热点研究阶段摘要
   - 数据治理 / atomic / compact 阶段摘要

产出物：
1. 一批已归档对象；
2. 更新后的 `ARCHIVE_CATALOG`；
3. 若干份阶段汇总文档；
4. 一份“当前默认阅读路径”收口结果。

验收标准：
- 未来 AI 不需要再反复读几十张旧过程卡才能理解历史；
- 历史信息没有丢，但被压缩成少数可读摘要；
- 默认入口层明显变薄，主树噪音显著下降。

### Phase 4：复用与重复实现治理规划
目标：在系统面和文档面收口之后，再决定代码层如何收口。

要做什么：
1. 固化已复用核心组件清单；
2. 固化相似未复用清单；
3. 按收益/风险给出治理优先级。

当前初步优先级：
1. 统一研究页 `SectionCard / Metric` 壳；
2. 清理情绪模块双轨实现；
3. 统一带股票上下文页面骨架；
4. 评估首页 / 复盘页主内容进一步收敛的可行性。

怎么做：
1. 先只出规划，不立即改组件；
2. 只在用户确认后，按小批次逐步推进；
3. 每次只做一类壳或一类重复实现，不混多个方向。

产出物：
1. 复用治理蓝图；
2. 分批次实施顺序。

验收标准：
- 后续代码治理有清晰顺序；
- 不会因为“看起来都像重复”而一次性动太多页面。

### Phase 5：专项执行
目标：在前 4 阶段都明确后，再进入定向清理与收口。

可能的执行批次：
1. 文档入口收口；
2. 历史过程卡降级 / 归档；
3. 阶段汇总文档落地；
4. `ops/` 脚本族分层与命名收口；
5. 研究页壳统一；
6. 首页 / 复盘页局部共享逻辑收口。

约束：
- 每批只解决一个问题面；
- 每批都要有回滚边界；
- 每批都要同步回填核心文档与治理卡。

## 6. 当前建议的实际推进顺序
如果按用户现在的优先级推进，建议顺序固定为：

1. **先做 Phase 2：过程材料降噪**
   - 这是当前最急的，因为它已经直接影响后续实现判断。

2. 再做 Phase 3：历史材料归档与阶段汇总
   - 这是从“减少误读”走向“减少垃圾材料体量”的关键一步。

3. 再做 Phase 1：系统地图正式固化
   - 让后续清理动作有统一参照系。

4. 再做 Phase 4：复用与重复治理规划
   - 为后面的代码收口准备边界。

5. 最后才做 Phase 5：专项执行
   - 避免一边清入口、一边改页面，导致范围失控。

## 7. 第一优先级专项：过程材料清理怎么做

### 7.1 本轮不直接删什么
本轮规划阶段不直接删除：
- `docs/changes/*`
- `docs/archive/*`
- `docs/strategy-rework/*`
- `docs/selection/*`
- `ops/*`

原因：
- 现在先要弄清楚“哪些是错的、哪些只是旧的、哪些仍有追溯价值”。

### 7.2 第一轮清理动作会做什么
后续执行第一批时，只做以下动作：
1. 列出高风险误导文档清单；
2. 给每项标记：
   - 当前是否仍是入口；
   - 是否已被更高层母卡覆盖；
   - 是否需要归档；
   - 是否只需加“先看新入口”的提示；
3. 先做最安全的降噪：
   - 改入口文档；
   - 降级旧卡；
   - 收缩默认阅读路径。
4. 然后立即进入归档准备：
   - 识别哪些对象可直接归档；
   - 识别哪些对象需要先抽取阶段摘要；
   - 识别哪些对象只保留索引，不再保留顶层暴露。

### 7.3 第一轮清理后希望达到的状态
1. 用户和 AI 默认只会先读：
   - `README.md`
   - `docs/00~08`
   - `docs/domain/*`
   - `docs/contracts/*`
   - `docs/ops/*`
   - 少数 current-state 母卡
2. 大量过程卡、旧实验、历史执行记录不再默认暴露；
3. 后续实现不再被过时说明带偏。
4. 第二批执行后，历史过程会从主树撤出一部分，并由阶段汇总承接可保留价值。

## 8. 风险与边界
- 风险 1：误把仍有价值的历史研究资料当垃圾删掉。
  - 约束：先降级、后归档、最后才考虑删除。
- 风险 2：入口文档改了，但历史卡没标记，依然会被全文检索误导。
  - 约束：对高频命中的旧卡补“先看当前母卡”的提示。
- 风险 3：同时动文档、脚本、页面，范围失控。
  - 约束：先文档降噪，再做脚本/代码治理。
